# ثنايا — ERP 03: استلام البضاعة من واجهة الإدارة (2 نوفمبر 2026)

## فرع مستقل يحتاج ترحيل قاعدة بيانات محمي
- الفرع: `feature/erp3-receiving-admin-ui-20261102` متفرع من PR #43 `feature/erp-goods-receiving-foundation`، وليس من PR #50.
- PR #43 أضاف جداول `PurchaseReceipt` و`PurchaseReceiptLine` وحقل `receiptRevision` إلى Prisma، مع عملية استلام ذرية واختبارات منفصلة. **هذه البنية غير موجودة بعد في قاعدة macOS الفعلية**.
- ممنوع تشغيل `prisma db push` أو ترحيل تلقائي على `backend/prisma/dev.db`. يلزم: نسخ احتياطي SQLite والملفات، فحص schema diff، بروفة على نسخة مؤقتة، خطة rollback، وبعدها ترحيل معتمد بشكل مستقل.
- عند دمج تغييرات أمان PR #45–#50 مع هذا الفرع، يجب إعادة اختبار Auth Cookies/CSRF وERP في فرع دمج خاص، لا يتم دمجها تلقائياً الآن.

## المنفّذ في هذه الدفعة
- صفحة `/admin/receiving` لاختيار أوامر الشراء المرسلة وتسجيل الاستلام الجزئي، بيانات التشغيلة والصلاحية عند الحاجة، ومرجع سند الاستلام.
- مراجعة قبل تثبيت حركة المخزون؛ إعادة قراءة الحالة من الخادم بعد الحفظ؛ مفتاح idempotency ثابت لإعادة المحاولة بنفس المحتوى، ويُجدّد إذا غيّر الموظف الحقول.
- عرض تاريخ السندات والكميات المتبقية، مع رسائل الأخطاء وطلب التحقق بعد الانقطاع.
- ربط `/admin/procurement` ونافذة الإدارة برابط الاستلام.
- إضافة `lotTracking` المشتق من المنتج إلى Snapshot الآمن للقراءة؛ اختبار يؤكد صحة الحقل دون كشف بيانات لا يحتاجها الموظف.
- هذه العملية تغيّر المخزون الفعلي بعد التأكيد فقط؛ **لا تصدر فاتورة مورد ولا تسجل ديناً أو دفعة**.

## المطلوب قبل استخدام الميزة
1. GitHub CI: بناء Backend وFrontend، واختبار `receiving.integration.cjs` على SQLite مؤقتة.
2. بروفة ترحيل schema وبيانات legacy بأوامر آمنة على نسخة احتياطية.
3. اختبار مستخدم حقيقي في بيئة اختبار: استلام جزئي، استلام مكمل، تشغيلة موجودة وأخرى جديدة، انقطاع اتصال وإعادة المحاولة، تعديل من موظفين بالتزامن.
4. الدمج المتسلسل PR #43 + PR #51 مع سلسلة الأمان PR #45–#50 في فرع مؤقت، والتأكد من أن إعدادات/الأذونات لا تتعارض.
5. بعد ذلك ERP 04 الموردون والذمم، ERP 05 تكلفة المبيعات، ERP 06 الصندوق، وبعد الوظائف نبدأ UI polishing للهوية الحالية (الأزرق الأصلي، وليس البرتقالي).

لا إطلاق أو تفعيل دفع حقيقي، ولا تغيير بيانات الزبائن الفعلية.
