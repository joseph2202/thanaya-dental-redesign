# ثنايا — Admin Workspace UX | 22 أكتوبر 2026

هذه دفعة تطوير واجهة إدارة المتجر على فرع `feature/admin-workspace-mobile` المبني من `feature/storefront-experience-polish`. لا تغيير في `Prisma` أو قواعد بيانات SQLite، ولا عمليات تعديل طلبات فعلية.

## النتيجة

### لوحة الإدارة المشتركة
- استبدال شريط التنقل الأفقي الطويل على الهاتف بقائمة جانبية احترافية تستخدم `<dialog>` أصلية، وتدعم زر الإغلاق وESC والخلفية المعتمة.
- شريط سريع للوحة التحكم، الطلبات، المنتجات، الإشعارات حسب **صلاحيات الدور الفعلي**. تبقى القائمة الدائمة على الكمبيوتر.
- إغلاق قائمة الهاتف عند تغيير الصفحة، وإظهار اسم الصفحة في الترويسة. **الواجهة ليست بديلاً عن صلاحيات API** الموجودة مسبقاً.

### المنتجات والمخزون
- على الموبايل: بطاقات منفصلة بكل منتج مع صورة أو أيقونة، الاسم، التصنيف، SKU، السعر، المتاح للبيع، الحالة (منخفض أو غير متوفر أو مخفي)، وأزرار المخزون/التعديل/الإظهار/الحذف حسب الصلاحيات.
- على الديسكتوب: الاحتفاظ بجدول كامل قابل للتمرير أفقياً عند الحاجة.
- فلاتر سريعة: الكل / مخزون قليل (1–5 متاحة للبيع) / غير متوفر (صفر) / مخفي. البحث باسم المنتج أو الماركة أو القسم أو SKU.
- التمييز في منتجات التشغيلات بين **المخزون الفعلي** والكمية **المتاحة للبيع** التي تستثني المنتهي الصلاحية، دون تغيير بيانات الخادم.
- مؤشرات تحميل/خطأ واضحة وإعادة المحاولة، بدلاً من اعتبار فشل الجلب أنه متجر فارغ.
- التمرير تلقائياً إلى محرر المنتج أو واجهة المخزون عند فتحها من بطاقة بعيدة أسفل القائمة.

### الطلبات
- عرض رمز قصير للطلب مع إمكان نسخ المعرّف الأصلي كاملاً؛ لا تغيير بالمعرّف الحقيقي أو بحث/مطابقة الخادم.
- زر اتصال بالزبون، وزيادة وضوح أزرار تغيير الحالة.
- اعتماد استجابة أحدث طلب تحميل فقط عند تغيير الفلاتر أو الصفحة بسرعة، حتى لا تظهر نتائج قديمة بعد الطلب الأحدث.
- ملخص أول نوعين في الطلب؛ **الفاتورة الكاملة** تبقى ضمن تفاصيل الطلب نفسها.
- إبقاء نوافذ التأكيد المخصصة لعمليات الإلغاء والمرتجع والانتقالات الحساسة كما هي، وعدم تعديل منطق الطلبات أو المخزون.

## حدود هذا العمل والتحقق

- هذه الدفعة **موجودة على GitHub فقط ولم تُسحب إلى Mac أو يُبْنَ frontend بها بعد**. لا تَدَّعِ نجاح اختبار لم يحدث.
- وفق تفضيل المستخدم، يُجرى **بناء واحد للواجهة بعد دفعة UI هذه**، ثم مراجعة سلوك الموبايل والكمبيوتر بصرياً. لا تعاد فحوصات أمان/طلبات/قاعدة البيانات لمجرد تغييرات عرض.
- اختبارات تكامل حقيقية لازمة عندما نبدأ تغيير قواعد المرتجعات أو الاسترداد المالي والتزامن، لأنها تؤثر في الحسابات وحركات المخزون.

## الأعمال المتبقية

- تحسين العرض الحي بعد معاينة الماك، ثم مرحلة مرتجعات تالفة وتسويات مالية فعلية مع قواعد الأعمال واختبارات منفصلة ضد قاعدة بيانات مؤقتة.
- سياسة إطلاق حقيقية (نسخ آلي، صور دائمة، قاعدة إنتاج، الأمان، مراقبة السرعة)، ولا نعيد فتح Quick Tunnel إلا بوعي أنه غير مناسب للنشر.
