# ثنايا — تأسيس تكاليف الشراء (المرحلة 2 من خطة الميزات التجارية)

> **مسودة غير مفعّلة**. أُضيفت جداول/حقول Prisma، لذلك **لا تشغّل db:push** قبل نجاح اختبار العزل ونسخة احتياطية صحيحة وفحص أي تحذير. لا تغيير للطلبات أو رصيد المخزون في هذا الفرع.

## الفكرة

- **المنتج القديم غير المتتبع للتشغيلات:** تكلفة شراء الوحدة `Product.purchaseCostIqd`، قد تكون `null` إذا مجهولة.
- **المنتج المتتبع للتشغيلات:** التكلفة على مستوى `ProductLot.purchaseCostIqd`، وهي مختلفة لكل شحنة.
- **الرقم هو تكلفة شراء مرجعية للوحدة بالدينار العراقي**، لا سعر البيع ولا رسوم التوصيل ولا صافي الربح.
- لا نحسب أرباح الطلبات القديمة ولا نكتب أي تكلفة أو ربح رجعي لها. ينبغي تصميم لقطات تكلفة مثبتة لحظة البيع في **دفعة لاحقة** قبل تقديم تقرير ربح حقيقي.
- العائد التقريبي من عرض المنتج، عند توفر سعر شراء: **سعر البيع الحالي − تكلفة الشراء الحالية**، قبل الخصومات ومصاريف الشحن والعمولات والمصاريف الثابتة والمرتجعات.
- **التحكم:** فقط owner/admin يستطيع تسجيل التكاليف. inventory يستطيع متابعة الكميات، لكن حقول التكلفة خاصة وتُحجب عنه وعن الزبائن.
- تغييرات الأسعار في `ProductCostChange` سجل تدقيق إضافي، لا تستبدل أي سجل بيع أو مخزون.
- مراجعات `costRevision` تمنع حفظ تغيير قديم من جهاز مختلف، وسجلات المبيعات للتشغيلة تمنع إعادة كتابة تكلفتها دون تسوية محاسبية.

## التنفيذ

- داخل `/admin/products` → المنتج → `المخزون` يظهر قسم **تكلفة الشراء** للإدارة.
- للمنتج العادي: أدخل تكلفة القطعة بالدينار واضغط حفظ.
- للمنتج ذي التشغيلات: تعديل تكلفة كل تشغيلة على حدة ما دامت **لم تُستخدم** في طلب.
- الخانة الفارغة تعني `غير معروف`، والصفر يعني تكلفة صفر فعلية (عينة مجانية مثلاً).
- قراءة سجل التغييرات: `GET /api/products/:id/purchase-cost/history`، خاصة بالإدارة.
- لا تمس هذه العملية `Product.stock`, `Product.price`, `Order.total` ولا `OrderItem.price`.
- لا تدخل بيانات تكلفة الشراء إلى JSON الخاص بصفحات المنتج أو البحث أو السلة أو فاتورة الزبون.

## اختبار وتشغيل محلي آمن

1. أوقف الباك إند والفرونت إند فقط عند مرحلة فحص الفرع الجديد والتشغيل.
2. على هذا الفرع شغّل `cd backend && npm run test:orders`، يتوقع **20 اختباراً** بقاعدة **مؤقتة**.
3. شغّل `cd frontend && npm run build`، وفحص إدخال 50,000 د.ع وتعديلها وإزالة التكلفة على نموذج آمن.
4. **بعد نجاح الفحوصات فقط** خذ نسخة احتياطية لقاعدة `backend/prisma/dev.db` عن طريق SQLite Online Backup API، واحفظ `backend/uploads`، وتحقق من `PRAGMA integrity_check` ومن أعداد الطلبات والمنتجات.
5. وبعد النسخة، الباك إند متوقف: `cd backend && npm run db:push`. عند أي `Reset` أو `Data loss` أو اقتراح حذف لا توافق. بعد نجاح schema التحقّق يرجع نشغل السيرفرين.
6. لا تُعطَ أسعار الشراء أو تقارير الهوامش التجريبية للزبائن ولا تُقدّم على أنها أرباح فعلية لصاحب المتجر.

## باقي الطريق المحاسبي
- تثبيت تكلفة المخزون/التشغيلة **عند تأكيد عملية البيع** في Snapshot غير قابل للتعديل.
- تقارير الهامش الإجمالي فقط للطلبات المسلمة ذات تكلفة معروفة كاملة؛ تفصل أجور الشحن والخصومات والتحصيل.
- معالجة المرتجعات الجزئية بالتشغيلة ورقم البند بدون مضاعفة أي قيد.
- صافي الربح الحقيقي يحتاج إجمالي المصاريف الفعلية ومدفوعات الموردين والمندوبين، مو مجرد سعر شراء.
