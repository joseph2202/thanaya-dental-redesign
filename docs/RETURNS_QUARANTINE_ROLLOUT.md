# ثنايا — استلام وفرز المرتجعات (السليم / التالف)

**الحالة: تطوير على فرع مستقل، يحتاج مراجعة واختبار آلي وترحيل قاعدة بيانات بموافقة المستخدم. لم تُمس قاعدة ثنايا الحقيقية.**

## المشكلة

قبل هذه الدفعة، استلام أي مرتجع كان يزيد `Product.stock` و`ProductLot.stock` بمجموع القطع المستلمة، حتى لو كانت بعض القطع غير صالحة للبيع. كذلك كان يوجد اختصار لتغيير حالة الطلب مباشرة إلى `returned` دون توثيق حالة القطع.

## ما أُنجز

- أُضيف حقل `OrderReturnLine.disposition`، بقيمتين مفترضتين `restocked` (صالح، يعود للمخزون) أو `quarantined` (تالف/غير صالح، يبقى في سجل الحجر **خارج** المخزون المتاح).
- القيمة الافتراضية `restocked` تعني أن سجلات الاستلام القديمة تبقى كما كانت دلالياً، ولا نعيد كتابة أرصدة الطلبات السابقة.
- يمكن استلام 3 قطع في الحدث نفسه: 2 سليمة و1 تالفة، أو توزيع الفرز بين تشغيلات مختلفة دون فقدان رقم التشغيلة.
- جميع القطع المستلمة (ومنها التالف) تُحتسب ضمن الرصيد المرجَع لمنع استلام نفس القطعة مرتين، لكن المخزون يزيد فقط بمجموع القطع السليمة.
- سجل `OrderReturnLine` هو سجل استقبال وحجر **وليس نظام إتلاف مادي أو رد أموال**. يلزم لاحقاً إقرار إتلاف/إعادة للمورد/فحص فني منفصل إذا أريدت سلسلة حيازة مكتملة.
- أُلغي من الـAPI اختصار تغيير حالة الطلب المُسلّم مباشرة إلى `returned`؛ الرد `409` يوجّه الموظف إلى واجهة الاستلام المفصلة. الحالة `returned` تُضبط آلياً عند اكتمال استلام القطع من خلال سجل المرتجع.
- الواجهة تعرض للسليم والتالف حقولاً منفصلة وملخصاً قبل التأكيد، وتعرض في سجل الطلب كمية السليم التي عادت للمخزون وكمية التالف المحجوز.
- لا تعديل على `Order.total` ولا إصدار رد مبلغ أو استنتاج أن الزبون استرد أموالاً.
- تظل صلاحية إدخال المرتجعات للمالك والمدير، وتبقى آلية idempotency برقم طلب العملية، وCAS لمراجعة الطلب قبل الحفظ.

## قاعدة البيانات — مهم جداً

**هذه ميزة تحتاج تغييراً حقيقياً في Schema، فلا تشغّلها على نسخة Mac الحية بمجرد سحب الفرع.** بعد `prisma generate` دون ترحيل الجدول القديم، قد يفشل تحميل المرتجعات. لا تخلط أجزاء هذا الفرع بفرع المعاينة الحي.

التغيير المطلوب — موثق للفحص، *ليس أمراً للتنفيذ الآن*:

```sql
ALTER TABLE "OrderReturnLine"
ADD COLUMN "disposition" TEXT NOT NULL DEFAULT 'restocked';
```

قبل أي ترحيل لقاعدة Mac: وقف الخدمات والنفق، تحقّق من عنوان `dev.db`، احفظ نسخة جديدة بالـ`safe_backup.py --backup`، افحص سلامتها وعدد السجلات، وطبّق على نسخة معزولة أولاً. التنفيذ على الأصل يحتاج موافقة المستخدم ومراجعة نتائج CI وخطة تراجع موثوقة. **لا `db:push` عشوائي ولا استعادة نسخة قديمة تمحو طلبات جديدة.**

## تجربة الترحيل بدون مساس البيانات الحقيقية

أضفنا `backend/scripts/rehearse_return_disposition.py`، وهو **للتمرين فقط**. يفتح SQLite المصدر بالقراءة فقط، ويأخذ نسخة خاصة في مجلد مؤقت، ويضيف الحقل **على النسخة المؤقتة حصراً**. بعدها يقارن بصمات السجلات القديمة، ويفحص SQLite integrity وforeign keys، ويتأكد أن المرتجعات القديمة تُوسم `restocked`. يمسح النسخة المؤقتة تلقائياً. **لا يحتوي على خيار `--apply`**.

في الماك يمكن تجربته على النسخة الاحتياطية التي تحققنا منها سابقاً `THANAYA-20261022-201539` (3 مستخدمين، 7 طلبات) دون تبديل فرع التطبيق إلى Schema الجديد:

```bash
cd ~/Documents/thanaya-dental-redesign
git fetch origin
git show origin/feature/returns-quarantine-foundation:backend/scripts/rehearse_return_disposition.py > backend/scripts/rehearse_return_disposition.py
python3 backend/scripts/rehearse_return_disposition.py --source "$HOME/Thanaya-Backups/THANAYA-20261022-201539/database.sqlite"
```

النتيجة المطلوبة: `ISOLATED REHEARSAL PASSED` و`Original database UNCHANGED`. هذه تجربة على صورة تاريخية وليست دليلاً على عدم تغير `dev.db` منذ تاريخ النسخة. للتفعيل الفعلي نحتاج نسخة حديثة، فحص مصدرها، توقف الخدمات، خطة تراجع وموافقة المستخدم المحددة.

## التحقق (بدون تحميل صاحب المتجر سلسلة فحوصات)

- `.github/workflows/returns-quarantine.yml` يفحص PR عند فتحه: `npm run test:orders` عبر قاعدة مؤقتة مُولّدة داخل `/tmp`، و`npm run build` للواجهة.
- تمت إضافة حالتي تكامل: مرتجع مختلط سليم/تالف، ومرتجع تشغيلتين مع قطعة سليمة وأخرى تالفة؛ تتحقق من التصرف بالرصيد، رفض التكرار، رفض تبديل حالة قطعة بنفس `requestId`، عدم تجاوز الكمية، والحفاظ على إجمالي الفاتورة.
- **نتيجة مؤكدة:** GitHub Actions run 39837654443 نجح في جميع اختبارات الطلبات (25/25) وبناء TypeScript backend وNext.js frontend بعد إصلاح مشكلة استنتاج أنواع بالواجهة. هذا لا يستبدل تجربة ترحيل جدول مرتجعات Mac على نسخة خاصة قبل التطبيق الفعلي.

## المراحل المتبقية

1. بعد اختبارات وفرز الحجر: **دفتر منفصل للاسترداد المالي** (مبلغ مدفوع/مستحق/مرجع، طريقة التسوية، إثبات، منع التكرار وحد أقصى متناسب)، دون الخلط بين دخول قطعة إلى الحجر وخروج نقد.
2. حساب تكلفة المبيعات التاريخية والتسويات والأرباح على أساس سجلات مؤكدة، وليس سعر تكلفة حالي.
3. فحص جرد الحجر ونقل القطع التالفة بشكل موثق إلى إتلاف أو رد للمورد (اختياري حسب سياسة المتجر).

**لا تخلط هذه المراحل المالية بنشر شكلي سريع؛ مرحلة الانبهار بالتجربة لا تعني التضحية بدقة الأموال والمخزون.**
