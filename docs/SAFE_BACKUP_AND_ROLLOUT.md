## قبل النسخ
1. أوقف سيرفري `npm run dev` للباك إند والفرونت إند (`Ctrl+C` في نوافذ Terminal) لضمان اتساق قاعدة SQLite مع ملفات الصور.
2. تأكد أن فرع العمل `feature/partial-returns-order-item-snapshots`، وألا توجد تغييرات محلية لم تُحفظ.
3. تأكد وجود مساحة كافية على القرص. لا تشارك `backend/.env` ولا محتوى `database.sqlite` ولا ملفات النسخ الاحتياطية في المحادثة أو على GitHub.

## التشغيل
من مجلد المشروع المحلي:
```bash
git pull --ff-only origin feature/partial-returns-order-item-snapshots
python3 backend/scripts/safe_backup.py --check-only
python3 backend/scripts/safe_backup.py --backup
```

### ماذا تنفذ أداة safe_backup؟
- تقرأ `DATABASE_URL` من البيئة أو `backend/.env`. إذا كان `file:./dev.db`، يُفسَّر نسبياً إلى `backend/prisma/`؛ لا تنشئ قاعدة جديدة حتى عند الخطأ.
- تتصل بالقاعدة عبر SQLite في وضع `mode=ro`، وتفحص `PRAGMA integrity_check` وأعداد `User, Product, Order, OrderItem, ProductLot, OrderItemLot, InventoryMovement, OrderReturn, OrderReturnLine` إن كانت موجودة (الفارغ `null` يعني الجدول لم يُنشأ بعد).
- النسخ يتم بواسطة `sqlite3.Connection.backup` إلى **`~/Thanaya-Backups/THANAYA-YYYYMMDD-HHMMSS/`** خارج المستودع، وليس بنسخ ملف SQLite يدوياً أثناء الكتابة.
- تفحص سلامة النسخة وأعداد الجداول مقابل المصدر، وتنسخ `backend/uploads/` إذا وجدت، مع مطابقة SHA-256 لكل ملف؛ ترفض الروابط الرمزية داخل الصور.
- تنشئ ملف `manifest.json` فيه بيانات إجمالية وأثر SHA-256 للـSQLite، بدون كلمات المرور أو سجلات الزبائن.
- إذا فشلت خطوة، تبقى نسخة باسم `INCOMPLETE-...` **غير معتمدة**، وتظهر رسالة الخطأ؛ لا تكمل أي ترحيل. احفظ النتيجة التشخيصية دون إرفاق قاعدة البيانات.

## بعد ظهور BACKUP VERIFIED
- راجع وجود `database.sqlite` و`manifest.json` و`uploads/` (إن وجدت)، واترك النسخة خارج GitHub.
- انسخ نسخة ثانية مشفرة إلى قرص خارجي آمن إذا البيانات فعلية؛ النسخة على نفس القرص لا تحمي من تعطل الجهاز.
- لم يحصل بعد أي `prisma db push` أو `Reset` أو تغيير قاعدة البيانات.
- أعطِ نتيجة الملخص (عدد الطلبات/المنتجات وسطر `BACKUP VERIFIED`) حتى نراجع **فروق Schema الفعلية** قبل اتخاذ قرار الترحيل.
- **لا توافق على تحذير `Data loss` أو `Reset` أبداً**. الترحيل اللاحق يُفحص خطوة خطوة وفي نسخة اختبارية أولاً؛ لا يُنفذ تلقائياً بمجرد نجاح النسخ.

## المرحلة التالية: تجربة Prisma على قاعدة مؤقتة فقط
بعد إيقاف الخوادم واسـتلام أحدث الفرع، شغّل:
```bash
cd ~/Documents/thanaya-dental-redesign
git pull --ff-only origin feature/partial-returns-order-item-snapshots
python3 backend/scripts/rehearse_schema.py --backup-dir ~/Thanaya-Backups/THANAYA-20261022-161653
```
- الأداة تقرأ النسخة الاحتياطية المعتمدة وتتأكد من checksum وSQLite integrity.
- تنسخ SQLite إلى مسار مؤقت خارج المشروع. تضبط `DATABASE_URL` لهذا المسار فقط.
- تشغّل Prisma `db push --skip-generate` **على النسخة المؤقتة فقط**، بدون أي علامة لتجاوز فقدان البيانات أو إعادة التصفير.
- بعد الترحيل التجريبي تتحقق من الجداول والأعمدة الجديدة، سلامة المفاتيح الخارجية وثبات عدد الصفوف لكل جدول قديم، ثم تحذف النسخة المؤقتة.
- عند أي تحذير أو فشل، تتوقف العملية من دون المساس بالقاعدة الأصلية. **لا تنفذ db:push على الأصل بعد الفحص وحده**؛ النتيجة تحتاج مراجعة قبل اتخاذ خطوة مستقلة.

## بوابة التفعيل المحلي (العمل الحقيقي يتطلب خطوات مستقلة)
**الشرط:** أوقف خادم الباكند والفرونتند وأي عمليات كتابة، ولا تستعمل خادماً آخر يشير إلى `backend/prisma/dev.db`. حافظ على النسخة الاحتياطية المعتمدة دون تعديل.

1. من جذر المشروع بعد سحب آخر فرع، شغّل **فحص ما قبل التطبيق (قراءة فقط)**:
```bash
python3 backend/scripts/verify_schema_activation.py --backup-dir ~/Thanaya-Backups/THANAYA-20261022-161653 --stage before
```
يجب أن تظهر `BEFORE VERIFICATION PASSED`، وهي تقارن **بيانات الصفوف القديمة** والأعداد مع النسخة الاحتياطية، وتتحقق من سلامة SQLite والعلاقات، وتوقفك لو اختلف المصدر.
2. إذا نجح الفحص وحده، شغّل Prisma بدون أي خيار لفقد بيانات أو مسح:
```bash
(cd backend && ./node_modules/.bin/prisma db push --skip-generate --schema prisma/schema.prisma)
```
هذا الأمر يغيّر **قاعدة SQLite الفعلية** ويجب تشغيله فقط بعد الفحوصات السابقة. **إذا ظهر Data loss أو Reset أو تحذير، لا توافق ولا تعِد تشغيله**؛ اطبع النتيجة وراجعها.
3. قبل تشغيل الخوادم، شغّل **فحص ما بعد التطبيق (قراءة فقط)**:
```bash
python3 backend/scripts/verify_schema_activation.py --backup-dir ~/Thanaya-Backups/THANAYA-20261022-161653 --stage after
```
يجب أن تظهر `AFTER VERIFICATION PASSED`. يتأكد الفحص من الجدولين والحقلين فقط، وعدم تغيّر السجلات القديمة وقيمها، وأن رجوع الطلبات القديمة لم يُسجّل تلقائياً. إذا فشل، **لا تشغل الخوادم ولا تحاول استعادة أو تعديل القاعدة بنفسك**؛ ارجع إلى رسالة الفشل لإعداد خطة استرجاع.
4. بعد الفحص الناجح، أنشئ نسخة جديدة `python3 backend/scripts/safe_backup.py --backup` للحالة بعد التفعيل، ثم ابدأ الخادمين؛ استخدم منتجات/طلبات تجريبية فقط لمراجعة الواجهات، الأسماء المحفوظة، ونوافذ المرتجعات الجزئية.
5. **ليست هذه عملية نشر Production**. ملفات SQLite والنسخ الاحتياطية فيها بيانات زبائن حساسة، وتبقى خارج GitHub وخارج المحادثة.
