# ثنايا — نسخة SQLite والصور قبل أي ترحيل

## حالة العمل (2026-10-22)
- أكد صاحب المتجر نجاح **23/23** اختبار باك إند معزول على `118a549`.
- أكد نجاح `npm run build` للفرونتند بعد إصلاح JSX على `df8dccc`.
- **لا يعني هذا أن Schema الجديدة موجودة في قاعدة بيانات الماك الحقيقية**. لا تشغّل الخادمين على الفروع ذات الجداول الجديدة قبل التحقق من توافق الـSchema والترحيل الآمن.
- هذه الخطوات هدفها **النسخ والتحقق فقط**. لا تغيّر الطلبات ولا المخزون ولا البيانات.

## قبل النسخ
1. أوقف سيرفري `npm run dev` للباك إند والفرونت إند (`Ctrl+C` في نوافذ Terminal) لضمان اتساق قاعدة SQLite مع ملفات الصور.
2. تأكد أن فرع العمل `feature/partial-returns-order-item-snapshots`، وألا توجد تغييرات محلية لم تُحفظ.
3. تأكد وجود مساحة كافية على القرص. لا تشارك `backend/.env` ولا محتوى `database.sqlite` ولا ملفات النسخ الاحتياطية في المحادثة أو على GitHub.

## التشغيل
من مجلد المشروع المحلي:
```bash
git pull --ff-only origin feature/partial-returns-order-item-snapshots
python3 backend/scripts/safe_backup.py --check-only
python3 backend/scripts/safe_backup.py --backup
```

### ماذا تنفذ أداة safe_backup؟
- تقرأ `DATABASE_URL` من البيئة أو `backend/.env`. إذا كان `file:./dev.db`، يُفسَّر نسبياً إلى `backend/prisma/`؛ لا تنشئ قاعدة جديدة حتى عند الخطأ.
- تتصل بالقاعدة عبر SQLite في وضع `mode=ro`، وتفحص `PRAGMA integrity_check` وأعداد `User, Product, Order, OrderItem, ProductLot, OrderItemLot, InventoryMovement, OrderReturn, OrderReturnLine` إن كانت موجودة (الفارغ `null` يعني الجدول لم يُنشأ بعد).
- النسخ يتم بواسطة `sqlite3.Connection.backup` إلى **`~/Thanaya-Backups/THANAYA-YYYYMMDD-HHMMSS/`** خارج المستودع، وليس بنسخ ملف SQLite يدوياً أثناء الكتابة.
- تفحص سلامة النسخة وأعداد الجداول مقابل المصدر، وتنسخ `backend/uploads/` إذا وجدت، مع مطابقة SHA-256 لكل ملف؛ ترفض الروابط الرمزية داخل الصور.
- تنشئ ملف `manifest.json` فيه بيانات إجمالية وأثر SHA-256 للـSQLite، بدون كلمات المرور أو سجلات الزبائن.
- إذا فشلت خطوة، تبقى نسخة باسم `INCOMPLETE-...` **غير معتمدة**، وتظهر رسالة الخطأ؛ لا تكمل أي ترحيل. احفظ النتيجة التشخيصية دون إرفاق قاعدة البيانات.

## بعد ظهور BACKUP VERIFIED
- راجع وجود `database.sqlite` و`manifest.json` و`uploads/` (إن وجدت)، واترك النسخة خارج GitHub.
- انسخ نسخة ثانية مشفرة إلى قرص خارجي آمن إذا البيانات فعلية؛ النسخة على نفس القرص لا تحمي من تعطل الجهاز.
- لم يحصل بعد أي `prisma db push` أو `Reset` أو تغيير قاعدة البيانات.
- أعطِ نتيجة الملخص (عدد الطلبات/المنتجات وسطر `BACKUP VERIFIED`) حتى نراجع **فروق Schema الفعلية** قبل اتخاذ قرار الترحيل.
- **لا توافق على تحذير `Data loss` أو `Reset` أبداً**. الترحيل اللاحق يُفحص خطوة خطوة وفي نسخة اختبارية أولاً؛ لا يُنفذ تلقائياً بمجرد نجاح النسخ.
