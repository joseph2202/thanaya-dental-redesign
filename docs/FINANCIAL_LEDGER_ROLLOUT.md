# ثنايا — سجل التحصيل والاسترداد المالي (مرحلة الأساس)

## لماذا بنيناه؟

الحالة `delivered` تعني أن الطلب مسلّم، **ولا تثبت قبض أي مال**. وحالة `returned` أو وجود سطر استلام مرتجع لا تعني أن المال رُدّ للزبون. لذلك نفصل الأحداث الثلاثة:
1. توصيل الطلب؛
2. استلام البضاعة المرتجعة السليمة/التالفة؛
3. **توثيق مبلغ تم قبضه أو رده فعلياً**.

## ما الذي أنجزناه

- أضيف جدول `OrderPaymentEvent` منفصل بسجلات إلحاق فقط من خلال API، مع رقم طلب، معرّف محاولة فريد، الموظف، نوع الحركة `collection / refund`، طريقة التعامل، المبلغ بالدينار، الملاحظة والتاريخ.
- أضيف `Order.paymentRevision` للمقارنة والتحديث الذري، حتى تتوقف العمليات المتزامنة إذا تغيّر السجل بين القراءة والكتابة.
- طلب التأكيد على نفس `requestId` يعيد السجل الموجود دون تكرار قبض أو استرداد. استعمال المفتاح نفسه مع بيانات مختلفة يُرفض.
- لا تحصيل قبل `delivered` / `returned`. لا يتجاوز مجموع المقبوضات `Order.total`.
- لا استرداد دون بنود استلام مرتجع فعلية في `OrderReturnLine`. المبلغ القابل للرد يُحدّ **تراكمياً** بقيمة البضاعة المرجعة بعد توزيع الخصم على البنود، وبما تم قبضه ولم يُرد بعد. كلفة الشحن ليست قابلة للرد تلقائياً.
- الموظف المسموح له بقراءة/إضافة عمليات السجل هو **owner أو admin**. لا يملك sales أو customer صلاحية الوصول إلى سجل الأموال.
- صفحة `/admin/finance` فيها ملخص الحركات حسب تاريخ إدخالها، وبحث عن سجل طلب، ونموذج تسجيل حركة مع تأكيد نهائي وتاريخ الحركات. أضيف رابط من لوحة الطلبات للطلبات المسلّمة والمرتجعة.
- **لا يوجد دمج مع بنك أو بوابة دفع**؛ البيانات تعكس إدخالاً يدوياً من موظف، وتستلزم إيصالاً/دليلاً فعلياً. لا يُطلق على الفرق «صافي ربح» أو «رصيد بنك».

المطلوب **قبل أي تشغيل للباكند الجديد على بيانات ثنايا**:
1. إيقاف Backend وFrontend والنفق الخارجي مؤقتاً.
2. إنشاء نسخة احتياطية **جديدة متحقق منها** باستخدام `backend/scripts/safe_backup.py`، وحفظها خارج GitHub.
3. تشغيل بروفة `backend/scripts/rehearse_finance_ledger.py` للقراءة فقط على المصدر؛ تعيد نسخة SQLite مؤقتة وتجرّب إضافة العمود والجدول والفهارس مع مقارنة جميع السجلات القديمة.
4. **أداة التفعيل المحمية أصبحت جاهزة في الكود ومختبرة على SQLite مؤقتة**: `backend/scripts/apply_finance_ledger.py`، وتفحص SHA-256 للنسخة الاحتياطية، عدد وسلامة صفوف كل الجداول، تطابق مخطط قاعدة البيانات، قفل SQLite حصرياً، وعدم تعديل أي بيانات قديمة. افتراضياً `--preflight` للقراءة فقط. `--apply` يتطلب موافقة صريحة مستقلة؛ **لم ننفّذه على قاعدة بيانات صاحب ثنايا**. ممنوع `prisma db push` على `dev.db` الحقيقي.
5. بعد إجراء النسخ الاحتياطي على **الفرع المحلي الحالي** وفي وقت لا يوجد فيه أي زبون يستخدم رابط Cloudflare، يتم سحب فرع المحاسبة الجديد وتشغيل البروفت `--preflight` قراءة فقط. لا تشغل الباكند الجديد قبل تطبيق الترحيل بصورة منفصلة ومعتمدة. بعد الترحيل المُصرّح به فقط `npx prisma generate` في backend وتشغيل النسخة الجديدة.

### أوامر المرحلة الحالية: نسخة احتياطية + بروفة قراءة فقط

بعد إغلاق `npm run dev` للباكند والفرونتند وإيقاف Cloudflare tunnel وبما أنه لا يوجد أي استخدام جارٍ للمتجر:

```bash
cd ~/Documents/thanaya-dental-redesign
python3 backend/scripts/safe_backup.py --backup
```

احتفظ بمسار `BACKUP VERIFIED:` الناتج؛ **لا ترسله للإنترنت ولا ترفعه إلى GitHub**. ثم من نفس مجلد المشروع:

```bash
git fetch origin
git switch --track origin/feature/financial-collection-ledger
python3 backend/scripts/rehearse_finance_ledger.py
```

بعدها نفّذ البروفت القراءة فقط باستبدال `THANAYA-YYYYMMDD-HHMMSS` بالاسم الحقيقي الذي ظهر بعد النسخ الاحتياطي:

```bash
python3 backend/scripts/apply_finance_ledger.py --preflight --backup "$HOME/Thanaya-Backups/THANAYA-YYYYMMDD-HHMMSS"
```

**توقف بعد البروفت. لا تشغّل `--apply` ولا تشغل الباكند الجديد في هذه المرحلة.** شارك فقط رسالة النجاح أو الخطأ بدون بيانات الزبائن أو ملفات SQLite.

**لا ترفع نسخة الاحتياط أو بيانات العملاء أو ملفات رفع الصور إلى GitHub**.
