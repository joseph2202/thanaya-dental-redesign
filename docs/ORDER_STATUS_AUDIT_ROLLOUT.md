# سجل حالة الطلب — نطاق التفعيل

## السلوك
OrderStatusEvent سجل append-only عبر API، مرتبط بالطلب والمنفذ مع نسخة من اسمه ودوره وقت الإجراء. ينشأ الحدث في نفس transaction لإنشاء الطلب أو تغيير حالته أو اكتمال استلام المرتجع. إذا فشل حفظ الدليل تتراجع الحالة والمخزون والإشعار معاً.

GET /api/orders/:id/history للـOwner/Admin/Sales فقط. لا يعرض هاتفاً أو عنواناً أو كلفة شراء أو actorId. يوضح completeFromCreation=false للطلبات التي لا تملك حدث إنشاء موثقاً. لا تتم تعبئة تاريخ الطلبات القديمة بأحداث مفترضة. المرتجع الجزئي له سجل استلام مستقل ولا يختلق انتقال حالة.

## المخطط
يضيف جدول OrderStatusEvent وعلاقتين وفهرسي orderId/createdAt وactorId/createdAt فقط. لا يغير أي حقل أو رصيد أو مبلغ قائم. Prisma Client الجديد يحتاج generate. لا تشغل كود الإجراءات على قاعدة قديمة دون تجهيز المخطط بمسار محمي.

## البروفة
على نسخة SQLite صناعية أو نسخة احتياطية خاصة ومعزولة:
`python3 backend/scripts/rehearse_order_history.py --source /path/to/disposable-copy.sqlite`

الأداة تفتح المصدر read-only، تنسخ إلى مجلد مؤقت، وتطبق الإضافة على النسخة فقط وتفحص fingerprint لكل الجداول السابقة وFKs والفهارس. ترفض مخططاً جزئياً أو symlink أو FK غير سليم، ولا تختلق أي حدث قديم. ليس لها وضع apply أو تفعيل حقيقي.

## التفعيل الحقيقي مؤجل
قاعدة Mac الحقيقية لم تقرأ أو تهاجر في هذه الدفعة. مسار تفعيل محمي ونسخة احتياطية موثقة وبروفة restore وموافقة المشغل تسبق أي اعتماد حقيقي، بما في ذلك متطلبات ERP05/06 السابقة. لا Prisma db push ولا reset. Preview المنفصلة تستخدم قاعدة مؤقتة بالمخطط الكامل؛ لا تنقلها إلى قاعدة المتجر.

## الفحوص
7 حالات Python للبروفة و9 حالات API فعلية تشمل الفاعل والصلاحيات والاسم/الدور وقت الإجراء، التكرار والتزامن والمرتجع الكامل والقديم وrollback عند عطل مخزن الأدلة. حالة Node الأخيرة تقارن بروفة Python بمخطط أنشأه Prisma نفسه.
